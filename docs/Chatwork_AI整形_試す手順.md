# Chatwork 内で「特定の書き方で投稿 → AI で整形して返す」を試す手順

**目的**: Chatwork 上で決まった文言で投稿すると、自社サーバーが Webhook で受け取り、Gemini で整形し、同じルームに Bot が整形結果を返す流れを試すための手順・方法です。**実装は行わず、手順と必要な検討だけをまとめます。**

---

## 1. やり方の整理

| 項目 | 内容 |
|------|------|
| **トリガー** | 「報告」「整形」など、決まった文言で投稿されたら処理する |
| **入力** | そのメッセージ本文、または「その直後のメッセージ」を整形対象とする |
| **処理** | Webhook で自社サーバーに通知 → 対象テキストを Gemini で整形 |
| **出力** | 整形結果を同じルームに Bot がメッセージで返す |

**できること**: Chatwork 内でいつも通りメッセージを書き、AI で通院報告フォーマットなどに整え、結果も Chatwork 内で確認できる。

---

## 2. 必要なもの一覧

| 種類 | 内容 |
|------|------|
| **Chatwork 側** | 対象ルーム（患者全体ルーム or 専用ルーム）への **Webhook 設定**（API 管理画面で 1 アカウントあたり最大 5 件） |
| **自社サーバー** | Webhook 受信用エンドポイント（POST）、署名検証、トリガー判定、整形処理、Chatwork 投稿 |
| **メッセージ取得** | 基本的に **Webhook のペイロードに `body` が含まれる**ため、トリガー付きの同一メッセージなら追加の「メッセージ取得 API」は不要。「直後のメッセージ」を使う方式のときだけ `GET /rooms/{room_id}/messages` の利用を検討 |
| **整形** | 既存の **Gemini（バックエンド）** を利用。通院報告フォーマット用のプロンプトを用意 |
| **ルール** | 「どのメッセージを整形するか」のルール（例: 本文が「報告」だけ / 「整形」で始まる / 自分へのメンションのときだけ など） |

## 3. Chatwork Webhook の仕様（確認済み）

- **通知**: メッセージ作成・編集・自分へのメンションを、設定した URL に **HTTPS POST（JSON）** で通知。
- **ペイロード例（メッセージ作成）**  
  `webhook_event_type: "message_created"` のとき、`webhook_event` に **`body`（本文）・`room_id`・`message_id`・`account_id`・`send_time`** が含まれる。
- **制約**  
  - **10 秒以内に応答**する必要がある。超過すると切断され、再送はない。  
  - レスポンスボディは **2,048 バイト以下**。  
  - 必ず **HTTP 200** を返す。
- **署名**  
  `x-chatworkwebhooksignature`（または `chatwork_webhook_signature`）で送信元検証。Webhook 編集画面のトークン + リクエストボディで HMAC-SHA256 検証が必須。

→ **「同じメッセージ本文」で整形する場合は、Webhook の `body` だけで完結可能。**  
「直後のメッセージ」を使う方式の場合は、Webhook 受信後に `GET /rooms/{room_id}/messages` で直近メッセージを取得する必要がある（後述）。

---

## 4. 「どのメッセージを整形するか」のルール案

実装前に、次のいずれか（または組み合わせ）を決めておく。

### パターン A: 同じメッセージ内でトリガー + 本文

- **例**: 「整形」で始まる 1 通のメッセージの、「整形」より後ろを整形する。  
  - 投稿: `整形\n今日は〇〇病院に行って…`  
  - 整形対象: `今日は〇〇病院に行って…`
- **メリット**: Webhook の `body` だけで完結。メッセージ取得 API 不要。  
- **ルール**: 本文が「整形」または「報告」で始まる場合、2 行目以降（または 1 行目以降のトリガー以降）を整形対象とする。

### パターン B: トリガー専用メッセージ + 「直後のメッセージ」を整形

- **例**: 1 通目に「整形」だけ投稿し、その直後に 2 通目で本文を投稿。2 通目を整形する。
- **必要なもの**: Webhook 受信後、`GET /rooms/{room_id}/messages` で直近 N 件を取得し、トリガー投稿より **あと** に送信されたメッセージのうち最新 1 件を整形対象とする（`send_time` やメッセージ順で判定）。
- **注意**: ユーザーが「整形」を送ってから少し遅れて 2 通目を送る場合、Webhook は「メッセージ作成」が 2 回飛んでくる。2 回目の Webhook で「直前が『整形』だけ」かどうかを判定するか、1 回目で「次のメッセージを待つ」ようにするか、仕様を決める必要がある。また、**10 秒制限**があるため、重い処理は非同期化（即 200 返却 → キューで整形 → 完了後に投稿）の検討が望ましい。

### パターン C: 自分へのメンションのときだけ整形

- **例**: `[To:123456] 整形 今日は…` のように Bot アカウントへのメンションで投稿されたときだけ処理する。
- **Webhook**: `webhook_event_type: "mention_to_me"` を使用。`body` にメンション記法が含まれるが、本文は取得可能。
- **メリット**: 通常の会話と分離しやすく、「意図したときだけ」動かせる。

**推奨**: まずは **パターン A**（同じメッセージ内で「整形」または「報告」で始まる投稿の続きを整形）で試すと、実装も検証も簡単です。

## 5. 処理フロー（試すときのイメージ）

1. **Chatwork**  
   ユーザーが対象ルームに「整形」で始まるメッセージ（または「報告」で始まるメッセージ）を投稿する。
2. **Chatwork**  
   メッセージ作成イベントが発生し、Webhook が自社サーバーの URL に POST する。
3. **自社サーバー**  
   - Webhook の署名検証（HMAC-SHA256）を行う。  
   - `webhook_event_type` が `message_created`（または `mention_to_me`）かつ、`body` がトリガー条件を満たすか判定。  
   - 満たす場合、整形対象テキストを決定（パターン A なら「整形」/「報告」以降の文字列）。  
   - （パターン B の場合は `GET /rooms/{room_id}/messages` で直後のメッセージを取得。）
4. **自社サーバー**  
   整形対象テキストを **Gemini** に渡し、通院報告フォーマット等で整形する。  
   - 既存の `carelifeController.js` の要約プロンプトを参考に、「通院報告フォーマットに整える」用のプロンプトを用意する。
5. **自社サーバー**  
   整形結果を **Chatwork API**（`POST /rooms/{room_id}/messages`）で同じ `room_id` に投稿。  
   - 既存の `postReportToChatwork` と同様に、`CHATWORK_API_TOKEN` と `room_id`（Webhook の `webhook_event.room_id`）を使う。
6. **自社サーバー**  
   Webhook リクエストに対して **10 秒以内に 200** を返す。  
   - Gemini + 投稿に時間がかかる場合は、**即 200 を返し、整形・投稿は非同期**（キューやバックグラウンド処理）で行う方式を検討する。

## 6. 試すための手順（段階的に）

実装はせず、以下を「やることリスト」として進めるとよいです。

### ステップ 1: Chatwork Webhook の準備

1. [API 管理画面](https://www.chatwork.com/service/packages/chatwork/subpackages/webhook/list.php) を開く。  
2. Webhook を 1 件追加する。  
   - **Webhook URL**: あとで用意する自社サーバーのエンドポイント（例: `https://your-backend.example.com/chatwork/webhook`）。  
   - ローカル検証する場合は **ngrok** などで HTTPS の URL を用意する。  
3. 設定後に表示される **署名検証用のトークン（秘密鍵）** を控え、サーバー側の環境変数（例: `CHATWORK_WEBHOOK_SECRET`）に格納する想定でメモする。  
4. **対象**: 全ルームに通知するか、特定のルームだけにするかは Chatwork の Webhook 設定で可能かどうか要確認（公式ドキュメントでは「参加するチャットルーム」でのイベントとあるため、Bot が参加しているルームが対象になる想定）。

### ステップ 2: 受信エンドポイントの仕様を決める

1. **パス**: 例として `POST /chatwork/webhook` または `POST /api/chatwork/webhook` を想定。  
2. **やること**:  
   - リクエストボディを JSON で受け取る。  
   - ヘッダー `x-chatworkwebhooksignature` と、Webhook 編集画面のトークンで署名検証。  
   - `webhook_event_type` と `webhook_event` を確認。  
   - トリガー条件に合致したら「整形対象テキスト」を取り出し、Gemini 呼び出しと Chatwork 投稿の処理に渡す（実装時はここに処理を書く）。  
3. **レスポンス**: 常に 200、ボディは空または短いメッセージ（2,048 バイト以下）。

### ステップ 3: トリガー条件の決定

1. 運用で使うトリガー文言を決める（例: 先頭が「報告」「整形」、または `[To:xxx] 整形` のようなメンション）。  
2. パターン A の場合: 「トリガー以降の文字列」の取り出しルール（1 行目のみトリガーとするか、トリガー語の直後から改行まで/末尾までなど）を文章で定義する。

### ステップ 4: 整形プロンプトの検討

1. 既存の `carelifeController.js` の通院報告要約用プロンプトを参考にする。  
2. 「Chatwork に書かれた自由文を、通院報告フォーマットに整える」用のプロンプト案を別ドキュメントやメモに書く。  
   - 入力: トリガー以降の 1 メッセージ本文。  
   - 出力: 見出し・日付・利用者名・病院・内容・申し送りなどの形式に整えたテキスト（既存と同様にマークダウン記号は使わない等のルールを揃える）。

### ステップ 5: 非同期化の要否

1. Gemini 呼び出し + Chatwork 投稿が 2〜5 秒で終わる想定なら、同期的に処理してから 200 を返すことも可能。  
2. それ以上かかる、または安定させたい場合は「Webhook では検証とキュー投入だけ行い、即 200 を返す → 別ワーカーで整形と投稿」とする方針を決める。  
3. 非同期にする場合、キュー（Cloud Tasks / メモリキュー / 別サービスなど）の候補をメモする。

### ステップ 6: 環境変数・シークレットの一覧

実装時に必要になるものをリスト化する。

| 変数名 | 用途 |
|--------|------|
| `CHATWORK_API_TOKEN` | メッセージ投稿用（既存） |
| `CHATWORK_WEBHOOK_SECRET` または `CHATWORK_WEBHOOK_TOKEN` | Webhook 署名検証用（Webhook 編集画面のトークン） |
| `GEMINI_API_KEY` | 整形用（既存） |

※ `CHATWORK_ROOM_ID` は、Webhook の `webhook_event.room_id` を使うため、固定のルーム ID は必須ではない（そのルームに返信する形になる）。

### ステップ 7: テストの進め方

1. **署名検証だけ**: Webhook URL にダミーエンドポイントを用意し、Chatwork から送られた POST のボディとヘッダーをログ出力。署名検証のコードが正しいか確認。  
2. **トリガー判定だけ**: `body` をログに出し、「報告」「整形」で始まるメッセージでだけ次の処理に進むことを確認。  
3. **整形だけ**: 手元でトリガー以降の文字列を Gemini に渡し、通院報告フォーマットが期待どおりか確認。  
4. **投稿だけ**: 整形結果のテキストを、既存の `postReportToChatwork` 相当で指定ルームに投稿できるか確認（既存の `scripts/post-to-chatwork.js` やバックエンドの実装を流用）。  
5. **一連動作**: 実際に Chatwork で「整形 …」と投稿し、同じルームに Bot が整形結果を返すまでを確認。

---

## 7. 注意事項（試す前に確認）

- **API 制限**: Chatwork API は同一ルームへ 10 秒あたり 10 回まで。連続で「整形」を送ると 429 になる可能性があるため、連打を避けるか、キューで間引くことを検討。  
- **Webhook の再送なし**: 一度失敗すると再送されないため、受信側は必ず 200 を返し、処理は可能なら冪等に。  
- **トークン・秘密鍵**: API トークンや Webhook 署名用トークンはコード・リポジトリに含めず、環境変数や Cloud Run のシークレットで扱う。

## 8. まとめ

| 項目 | 内容 |
|------|------|
| **トリガー** | 「報告」「整形」など決まった文言で投稿（同じメッセージ内でトリガー+本文がおすすめ） |
| **入力** | Webhook の `body` からトリガー以降を整形対象にする（パターン A） |
| **処理** | 自社サーバーで署名検証 → トリガー判定 → Gemini で整形 → 同じ `room_id` に投稿 |
| **既存資産** | Chatwork 投稿（`postReportToChatwork`）、Gemini 要約（`carelifeController.js`）を流用可能 |
| **新規に用意** | Webhook 受信エンドポイント、署名検証、トリガー判定、整形用プロンプト（と必要なら非同期キュー） |

この手順に沿って、まずは「どのルールで・どのパターンで試すか」を決め、その後で実装に進むとよいです。
